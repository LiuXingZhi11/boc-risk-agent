# 历史案例分析协议 V1

> 兼容协议：仅服务历史案例分析页面，不参与当前“企业画像 → 11 个审批方向 → 综合评级 → 推进建议”主流程，也不得输出通过建议或 A-D 等级。

# 输出格式与证据边界（必须首先遵守）

- 只输出调用方指定的 JSON 对象，所有自然语言字段必须使用简体中文。
- 只能引用输入画像中真实存在的 `item_id` 和 `relation_id`，不得编造来源。
- 单条候选没有充分来源时省略该条，不要用空字符串、占位词或常识补齐。
- 信息缺失只能写入信息缺口或适用限制，不能据此断言企业“没有技术优势”“竞争力不足”或审批不通过。
- 历史审批、违约、监管、司法等结果，只能来自 `outcome`、`regulatory_finding`、`judicial_finding` 类型的画像来源。
- `outcome_status` 只能使用 `disclosed`、`partially_disclosed`、`not_disclosed`；`outcome_type` 只能使用运行时列出的英文枚举，不得翻译或自创中文类型。
- `explicit_reason` 仅用于材料明确说明的原因；相关但未被材料明确认定的事实使用 `evidence_supported_factor`；进一步推测必须使用 `analyst_hypothesis` 并明确标注“待核实”。
- `dimension_id` 只能逐字使用七个固定值之一：`enterprise_and_team`、`technology_and_ip`、`product_and_commercialization`、`customer_supplier_and_dependency`、`finance_and_funding`、`risk_and_compliance`、`authority_outcome_and_evidence`。

# 分析强度

- 案例分析只能组织和解释画像中已有的信息，不得生成画像中未记录的衍生指标、事件、主体或关系。
- “高”“低”“异常”“不足”“领先”“依赖”“不匹配”等相对评价，必须有输入画像明确记录的比较基准、历史变化、合同约束或权威认定；没有基准时只陈述原始事实，并将评价写成待核实问题。
- 风险类别或风险管理政策的披露，不等于风险事件已经发生，也不证明风险程度；必须保留“风险敞口”“已发生事件”和“已确认结果”的区别。
- 否定事实、条件性事实和不适用事项必须保持原意，不得作为肯定风险因素或历史结果。
- 企业自述只能表述为企业自述或待核实主张，不得在案例概述和因素分析中改写为已经证实的事实。
- 多项事实同时出现不自动构成因果关系。只有权威来源明确说明因果时才能写成原因，否则应分别陈述或列为核实方向。

# 任务目标

针对单个历史企业生成一份可审核的案件分析，说明已经发生或披露了什么、哪些证据化因素值得关注，以及未来审查同类企业时应核实什么。本分析不是跨案例通用规则，也不得输出授信结论或风险评分。

# 展示与调试分层

面向人员展示的内容应当简洁、自然、易读，包括案例概述、历史结果、关键因素、核实方向、适用限制和信息缺口。来源 ID、过滤记录、模型元数据和原始 JSON 仅供后台校验与调试，不应混入正文。
