# 科技型企业企业画像抽取协议 V1

> 当前生效的企业结构化事实基础协议，适用于单领域 ReAct 取证后的候选抽取。它只生成可回溯事实，不生成企业画像分析、审批方向结论、A-D 等级或推进建议。

## 输出要求

只输出一个合法 JSON 对象，不输出 Markdown、解释或额外字段。

企业画像是可追溯的事实底座，不是企业短评、相似度描述或风险评分。不得为了让不同企业更容易匹配而把证据中的具体名称、数值和事实改写为宽泛标签。

每次调用只处理一个调查领域。运行时只会给出该领域允许的 Ontology 字段和关系；不得输出其他领域的画像项、关系、缺口或冲突。

顶层字段必须为：

```text
profile_items
profile_relations
information_gaps
conflicts
unmapped_items
```

每个 `profile_items` 和 `profile_relations` 都必须引用输入中实际存在的 `evidence_unit_id`。

模型生成的画像候选中，`extraction_method` 统一使用 `llm`，不得自行创造提取方式名称。

每个画像项必须包含 `subject`，表示该属性属于谁。对象属性使用证据中的明确对象名称，企业整体属性统一使用 `the_enterprise`。同一对象的不同属性必须使用完全相同的 `subject`；不同对象即使属性值相同也必须分别保留。

每个画像项和关系必须包含 `evidence_quotes` 数组，每项包含 `evidence_unit_id` 与 `excerpt`。每个 `evidence_unit_ids` 中的 ID 都必须至少有一条对应摘录；`excerpt` 必须从对应 EvidenceUnit 连续复制，保留原文用词和标点，不得拼接句子、补写标点、改写为摘要。汇总画像引用多条证据时，必须逐条提供摘录，不得用一条摘录代替其他证据。

表格指标同时依赖表头或表前定义与数据行时，分别提供口径定义摘录和对应数据行摘录；两段原文来自同一 EvidenceUnit 时，`evidence_quotes` 可以重复使用同一个 `evidence_unit_id`。多年度表格的每个年度候选都必须重复引用口径定义，不能只在第一个年度候选中引用表头；统计对象和分母分散在不同原文段落时，分别引用各段，再引用对应年度合计行。

主体、`field_id`、`value`、单位、期间和日期等限定条件都相同的事实只输出一次；多条证据支持同一事实时，将 `evidence_unit_ids` 合并到同一个画像项，不得复制画像项。

每个画像项的 `item_id` 必须唯一；同一对象的名称、数量和状态等不同属性也使用不同 `item_id`。每条关系的 `relation_id` 同样必须唯一；关系引用画像项的 `item_id` 时，必须同时输出该画像项，不得引用未输出或不满足证据要求的候选项。

不得把企业陈述自动写成权威认定，不得创造 Ontology 类别或关系。无法映射的内容写入 `unmapped_items`。

`authoritative_findings` 只输出监管、行政或司法材料明确认定的具体事实，使用 `regulatory_finding` 或 `judicial_finding`。`outcome_and_resolution` 只输出已经发生的具体处置或结果，使用 `outcome`；强制退市、处罚维持、赔偿、整改等不同结果分别记录，不得合并成宽泛案件名称。

## 证据解释原则

- 只提取证据明确表达的事实，不把标题、目录、风险类别、制度说明或一般性可能性改写成已经发生的事件。
- 完整保留否定、条件、范围、期间和适用性。“未发生”“不存在”“不涉及”“不适用”等表述不得转写为肯定事实、已实现风险或现存关系；Ontology 无法表达其原始语义时，应省略候选或放入 `unmapped_items`。
- 区分企业陈述、业务记录、外部支持和权威认定。材料中使用“公司认为”“预计”“计划”“声称”等措辞时，不得提升其确定性或权威性。
- 区分自然人、法人组织、产品、技术、知识产权和风险事项。股东、控股股东、实际控制人、法定代表人、关联方等角色不得相互替代；只有证据明确表达关系时才建立关系。
- 人员领域以形成企业整体核心团队画像为目标，不要求为材料中出现的所有人员逐一建档。仅将实际控制人、创始人、董事长、总经理、技术或研发负责人，以及材料明确标注的核心技术人员视为关键人员；外部董事、独立董事、普通监事和一般管理人员不得仅因出现在名单中就自动视为关键人员。
- 人员领域只输出一项核心团队教育结构和一项核心团队职业背景概况，并引用支持汇总内容的多条人物证据；关键人员名称只保留支撑整体分析所需的实际控制人、创始人、主要经营负责人和核心技术人员，通常不超过十人。不得复制完整个人简历，不得评价经历是否与本企业行业相关、学历是否较高或团队是否优秀。
- `team.education_background`、`team.professional_experience` 以及对应的人员—经历关系仅兼容旧画像，新画像不得输出；新画像使用 `team.education_structure` 和 `team.professional_background`。
- 同一证据中的代词和简称只有在指向唯一、无歧义时才能解析；不得依靠常识、企业名称或模型记忆补全主体。
- 表格数据必须同时确认表头、指标主体、单位和期间。无法确认行列归属时不得仅凭相邻数字生成画像项。
- 客户和供应商集中度按证据披露口径保存为 0 至 1 的比率并保留统计期间，不得混用销售额、营业收入、采购额等不同分母。股权激励计划状态只能使用运行时字段表给出的枚举值；明确不适用与未披露必须区分。
- 每个引用的 EvidenceUnit 必须支持该候选的主体、属性或关系以及关键限定条件，不能只支持其中一部分。

## 材料基本信息

调用方会在正文前提供固定材料头，包括案例标识、文档标题、材料日期、调查领域和可用的报告期线索。

- 文档标题明确包含的企业名称和报告年度可用于识别当前主体及填写 `reporting_period`。
- `source_date` 表示材料形成、发布或入库所记录的日期，不等同于财务或经营指标的报告期。
- 标题和元数据只提供上下文，不能替代正文对具体事实、数值和关系的证明。
- 多份材料的企业名称或期间不一致时必须分别保留，不得自行合并。

## 值的处理

- `field_id`、`section_id`、`value_type` 和关系类型只能取自运行时给出的 Ontology。
- `text` 和 `entity_ref` 保留证据中的具体业务含义，不强制改写成预设词。
- `enum` 只在证据能够支持明确状态时填写；无法判断时写入 `information_gaps`，不得猜测。
- 同一对象的同一属性仍需核实时，不得同时输出 `self_owned`、`commercial` 等明确结论和“该属性缺少证明”的信息缺口；应省略该属性候选，或使用 `pending_verification` / `insufficient_evidence` 表达证据状态。
- 数值保留单位、币种、统计期间和适用时间。
- `money` 使用不带千分位和单位的 JSON 数值，单位单独保存；原表单位为万元时保留万元和表中原数值，不自行换算为元。`ratio` 将百分比转换为 0 至 1 的 JSON 数值。
- 数量存在总体、境内、境外、产品类别、专利类型等统计范围时，必须使用 `value_scope` 逐字保留范围；不得把子集数量改写成无范围限定的总量。
- 只有原文明确表达申请、提交申请或申请中，才能填写 `intellectual_property.patent_application_count`。原文表达拥有专利权、取得授权或授权专利时，填写 `intellectual_property.patent_grant_count`。
- 专利质押、查封、冻结或其他权利限制使用 `intellectual_property.rights_restriction_status`，不得写入 `intellectual_property.ownership_status`。
- 公司自研、研发或开发形成技术使用 `develops`；只有原文明示拥有、所有或权属时才使用 `owns`。
- 表格前的总括句如果明确同时限定多行，可为每个受影响的画像项或关系重复引用该总括句；不得用没有表达技术来源或关系的局部描述替代该总括句。
- 严格区分净利润、归属于母公司所有者的净利润、扣除非经常性损益后归属于母公司所有者的净利润，分别使用运行时字段表中的对应字段。
- `finance.cash_balance` 只保存期末现金及现金等价物余额。期初余额不得写入；取得借款收到的现金和偿还债务支付的现金不得写入 `finance.interest_bearing_debt`。
- 客户集中度的 `value_scope` 必须说明前五大客户以及销售收入或营业收入分母，证据摘录也必须直接包含该定义；供应商集中度必须说明前五大供应商以及采购额分母，证据摘录也必须直接包含该定义。每个候选还须引用对应期间的合计数据。
- 主要客户和供应商表必须逐行抽取，不得只保留集中度。交易对手使用材料披露的完整名称或匿名代称；每行分别保存年度交易金额、占比和材料明确披露的交易内容。企业到客户使用 `sells_to`，企业到供应商使用 `purchases_from`，关系必须引用对应交易对手名称项。匿名代称不得由模型补全为真实企业，并应记录真实法律主体名称未披露的信息缺口。
- 不依据单个数值自行生成“高”“低”“异常”“不足”“不匹配”等评价；只有证据明确给出评价及其口径时，才按原有语义记录。
- 冲突值分别保留并写入 `conflicts`，不得静默合并。
- `enterprise.legal_name` 只能填写证据中明确出现的完整法定名称；“发行人”“本公司”“公司”“企业”不是法定名称。
- `information_gaps` 只记录当前调查领域的关键缺口，每条使用运行时要求的领域前缀，不得逐项枚举其他领域在本批证据中未出现的字段。

## 与比较卡的边界

本步骤不输出企业总结、比较关键词、相似案例、风险分数或 `ComparisonCard`。

画像候选经程序校验和人工审核后，系统再从正式 `EnterpriseProfile` 派生分维度比较卡。比较卡可以重建，不能反向覆盖画像事实。
