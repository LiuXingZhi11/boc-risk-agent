# 企业结构化事实抽取

> 审阅镜像。基础业务协议为 [科技型企业企业画像抽取协议_V1.md](科技型企业企业画像抽取协议_V1.md)；运行时还会注入当前领域字段白名单、关系白名单、证据正文和领域专项规则。

```text
你负责从给定证据中生成科技型企业画像候选。
只输出 JSON 对象，不输出 Markdown 或解释。
企业画像是有证据约束的事实底座，不是企业短评、相似度描述或风险评分。
不得创造 Ontology 类别或关系；每个 profile_item 和 profile_relation 必须引用输入中真实存在的 evidence_unit_id。
企业陈述、外部支持和权威认定必须区分；无法确定的内容放入 information_gaps 或 conflicts。
保留证据中的具体名称、数值、单位和期间，不要为了后续匹配而改写为宽泛标签。
只抽取当前调查领域，不得顺便补充其他领域的画像项、关系或信息缺口。

输出字段：profile_items、profile_relations、information_gaps、conflicts、unmapped_items。
profile_items 每项包含 item_id、subject、section_id、field_id、value、value_type、information_status、content_role、
evidence_unit_ids、evidence_quotes、extraction_method，以及可选的 value_scope、unit、source_date、reporting_period、event_date、effective_date。

每个 evidence_unit_ids 中的 ID 都必须至少有一条对应摘录；摘录必须从对应 EvidenceUnit 连续复制，保留原文用词和标点，
不得拼接、补写标点或改写为摘要。表格指标依赖表头与数据行时，分别提供定义摘录和数据行摘录。

field_id、section_id、value_type 只能从运行时注入的 Ontology 字段表逐字选择；
relation_type 以及 source_type/target_type 只能从运行时注入的关系表逐字选择；
evidence_unit_ids 只能从运行时白名单逐字复制。

无法确定时写 information_gaps，不得猜测。未披露不等于零；比例必须由原文直接披露，模型不得自行计算；
不得把否定事实（如“无重大诉讼”）写成风险事项。
```

## 领域专项规则来源

以下规则仍动态保存在 `src/profiles/extraction.py` 的 `domain_rule` 中，并会随领域注入：

- `team`：关键人员范围、团队教育/职业背景汇总规则；
- `technology_and_ip`：专利申请/授权/范围、技术成熟度、权利限制规则；
- `finance_and_funding`：净利润口径、现金余额、有息负债、比例规则；
- `enterprise_and_control`：主营业务和企业发展阶段规则；
- `product_and_project`、`market_and_commercialization`：产品与技术、项目、客户的边界；
- `risk_matters`、`authoritative_findings`、`outcome_and_resolution`：风险、监管司法认定、处置结果的边界；
- `customer_and_supplier`：前五大客户/供应商逐行抽取、集中度与关联关系规则。

这些规则直接对应 Python 校验，后续迁移时必须与校验规则一并审阅，不能只改单独的提示词。

## 当前固定调查范围：10 个结构化事实领域

每次模型调用只处理其中**一个**领域；不允许跨领域顺手补充事实。

| 领域 ID | 业务含义 | 允许抽取的主要字段 |
|---|---|---|
| `enterprise_and_control` | 企业主体、主营业务、发展阶段、实际控制关系 | 法定名称、成立日期、发展阶段、主营业务、实际控制人 |
| `team` | 实控人、核心团队与激励 | 实控人、关键人员、教育结构、职业背景、股权激励状态 |
| `technology_and_ip` | 技术体系与知识产权 | 技术名称、来源、成熟度、权属；专利名称、申请/授权数量、权属和权利限制 |
| `product_and_project` | 产品及技术转化对象 | 技术名称、产品名称、产品商业化阶段 |
| `market_and_commercialization` | 产品市场化与商业化 | 产品名称、产品商业化阶段 |
| `customer_and_supplier` | 客户、供应商、交易与集中度 | 前五大客户/供应商集中度、交易对手、金额、比例、内容、关联关系 |
| `finance_and_funding` | 财务、研发与债务基础 | 营收、经营现金流、净利润、归母/扣非归母利润、研发投入及比例、现金余额、有息负债 |
| `risk_matters` | 企业已披露风险事项 | 风险事项；不含监管/司法认定和已发生结果 |
| `authoritative_findings` | 监管、行政、司法明确认定 | 风险事项，但内容角色必须为监管或司法认定 |
| `outcome_and_resolution` | 已发生处置或最终结果 | 风险事项，但内容角色必须为处置或结果 |

完整字段字典、字段类型、枚举值和关系类型见 [../ontology/manifest.yaml](../ontology/manifest.yaml)。运行时会把当前领域对应的字段和关系白名单完整注入模型。

## 审查逻辑（当前实现）

1. ReAct 阶段先从证据目录中定位当前领域材料，再读取证据正文；
2. 每次抽取只针对一个领域，按上表字段白名单逐项寻找可直接支持的事实；
3. 对每个候选事实，先确定主体、字段、数值/状态、期间、单位和统计范围，再复制连续原文摘录；
4. 有明确原文和字段口径时输出 `profile_item`；有明确主体—对象—谓词关系时输出 `profile_relation`；
5. 证据不足、原文有冲突或口径不能确定时，不猜测，写入 `information_gaps` 或 `conflicts`；
6. Python 再检查字段白名单、类型、期间/单位、摘录是否存在、数值口径和专项规则；未通过者不会入库，可触发定向补查。

因此这一层的目标是“可回溯事实”，不是判断企业好坏。技术、财务、风险的好坏分析在后续主题分析和审批方向报告阶段完成。
