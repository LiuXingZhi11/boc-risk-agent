# 业务可维护提示词与字段规则实施手册

> 本文件说明业务人员可以维护的提示词和字段规则。运行时会从 `prompts/` 读取这些内容；程序接口、数据库结构和字段 ID 仍由开发人员维护。

## 1. 目标

将可由业务人员维护的模型任务规则与字段语义规则从 Python 字符串中抽离，改为 Markdown 文件作为运行时唯一的固定规则来源。业务人员修改规则后，无需改代码即可在下一次模型调用中生效。

本次不改变 Ontology 的字段 ID、字段类型、枚举值、证据校验或数据库结构；字段级约束由 `prompts/data/企业画像本体.yaml` 定义，跨事实约束由 `prompts/data/企业画像校验规则.yaml` 记录并由 Python 校验负责。

## 2. 边界

### 2.1 Markdown 维护

- 模型任务目标、审查顺序、输出业务要求；
- 每个画像领域可提取的业务范围；
- 每个字段的可归入表述、排除表述、相邻字段边界；
- 字段应保留的主体、期间、单位、统计范围和证据要求；
- 业务判断规则，例如审批方向、排名和综合评级的语言口径。

### 2.2 Python 维护

- 当前企业、行业、审批点、证据正文、证据 ID 和指标的运行时注入；
- `field_id`、类型、枚举值、关系端点和 JSON 输出的确定性校验；
- ReAct 工具、调用上限、数据库读写和审批状态流转。

Markdown 不能直接放入未经约束的自由字段或任意 JSON 结构；业务规则只能影响模型理解，不能绕过 Python 校验。

## 3. 本次实施范围

1. 在 `prompts/data/企业画像本体.yaml` 的对应字段中维护字段定义、同义词和抽取边界；
2. 企业 ReAct 证据调查现在读取 `prompts/data/企业画像数据规则.md` 的对应章节；
3. 将企业结构化事实抽取的领域专项规则改为从字段规则 Markdown 按领域读取；
4. 企业结构化事实抽取现在读取 `prompts/data/企业画像数据规则.md` 的“结构化事实抽取”章节；
5. 将企业关系修复、主题分析、行业 ReAct、行业背景、审批方向和同行排名一并改为加载对应 Markdown；
6. 在 `prompts/提示词目录说明.md` 中明确哪些文件是运行时来源，哪些属于兼容功能；
7. 用现有单元测试验证模板加载、字段规则读取和企业画像流程未破坏。

行业背景提示词位于 `prompts/data/行业背景数据规则.md`；审批方向、同行排名和综合评级已经合并到 `prompts/logic/授信审批逻辑规则.md`。运行时仍由 Python 注入企业、证据、审批点和比较卡等数据，并继续负责结构校验。

## 4. 实现步骤

1. 编写字段规则 Markdown：每个领域单独成节，使用稳定的领域 ID；
2. 增加简洁的 Markdown 模板与章节加载函数，缺少指定章节时明确报错；
3. ReAct 调查将当前企业、领域目标、查询和调用上限替换进 `01` 的占位符；
4. 事实抽取加载 `02` 的固定协议，并读取当前领域的字段规则；
5. Python 继续从 manifest 生成字段、关系和证据白名单，并保留原有候选校验；
6. 更新提示词目录与测试，确认业务人员修改的 Markdown 已被运行时读取。

## 5. 验收标准

- 修改 `01` 中的固定调查文字会改变 ReAct 运行时 system prompt；
- 修改字段规则文件中某领域的文字会改变该领域事实抽取 prompt；
- 抽取 prompt 仍包含当前字段白名单、关系白名单、证据 ID 与证据正文；
- 其他领域不能读取本领域以外的字段规则；
- 现有测试全部通过。

## 6. 结构化事实抽取枚举兼容修复

### 需求

DeepSeek 在结构化事实候选中可能把模型抽取方式写成 `direct_extraction`，而本体允许的 `extraction_method` 枚举是 `llm`、`rule`、`import`、`manual`。模型抽取事实应统一记录为 `llm`，不能因为别名导致正式画像入库失败。

### 实现步骤

1. 在结构化事实提示词中明确 `extraction_method` 的允许值，并指定本次模型抽取使用 `llm`。
2. 在候选转正式画像的边界处，将已知别名 `direct_extraction` 规范为 `llm`。
3. 增加单元测试，确认别名可以入库且其他非法值仍然按照原规则报错。
