# 数据、逻辑、行动、权限内容组织手册

## 1. 目标

将系统中由业务人员可维护、并可能作为大模型输入的内容，按职责拆分为“数据、逻辑、行动、权限”四层。业务规则不再散落在 Python 字符串中；代码只负责注入运行时数据、调用模型、校验结构和执行已确认的流程。

本次整理不改变既有审批口径，也不新增自动授信动作或真实权限拦截。

## 2. 四层边界

| 层级 | 职责 | 主要维护内容 | 不应承担的职责 |
|---|---|---|---|
| 数据 | 将原始证据转成可追溯的结构化信息 | Ontology、字段语义、事实抽取、关系修复、行业背景抽取 | 排名、审批结论、授信动作 |
| 逻辑 | 基于已获授权的数据进行检索、分析、比较和判断 | ReAct、主题分析、审批方向、同行排名、综合评级 | 绕过字段权限、直接执行外部动作 |
| 行动 | 将已形成的结论转成需人工确认的跟进事项 | 补件、核验、持续监测、人工复核 | 自动放款、自动拒绝、自动修改原始事实 |
| 权限 | 在数据进入界面或模型前定义谁可见、谁可操作 | 角色、字段可见范围、操作范围、审计要求 | 由大模型自行决定权限 |

## 3. 目录与迁移原则

```text
prompts/
  data/      # 数据层模型指令
  logic/     # 逻辑层模型指令
  action/    # 行动层规则；当前仅为人工跟进骨架
  提示词目录说明.md  # 全量索引、运行状态、维护边界
prompts/data/ # 数据层稳定 Schema、字段语义与数据抽取协议
authorization/ # 非模型权限设计；当前未接入运行时拦截
```

1. 以“模型输出是什么”为首要分类依据：输出事实或行业资料，归入数据；输出判断、排名、报告，归入逻辑。
2. 文件迁移后，所有代码和脚本必须改为新路径；不得保留同名旧副本，避免业务人员改错文件。
3. `prompts/data/企业画像本体.yaml` 只负责对象、关系、字段 Schema 和程序接口；`prompts/data/企业画像字段语义.yaml` 负责业务语义；通用抽取规则放在 `prompts/data/企业画像抽取规则.yaml`，跨事实校验约束放在 `prompts/data/企业画像校验规则.yaml`；本体设计手册只放在 `docs/project/`，不作为模型输入。
4. 权限规则由服务端在检索、展示和拼装模型输入之前执行；即使未来有权限提示词，也只能解释已过滤范围，不能决定放行。

## 4. 实施步骤

1. 建立四层目录和统一索引。
2. 将已有提示词按数据层、逻辑层迁移；为行动和权限建立可维护的初始规则文件。
3. 更新 Python、脚本、文档中的全部提示词路径。
4. 搜索旧路径，确保没有运行时引用残留。
5. 执行提示词加载、企业结构化事实、ReAct 工作流相关测试。

## 5. 验收标准

- 业务人员从 `prompts/提示词目录说明.md` 能知道每个文件是否正在运行时生效、由哪个模块调用、可修改什么。
- 每一份模型提示词只存在一个权威位置，且位于与职责一致的层级目录。
- 字段类型、枚举、证据 ID 和 JSON 校验仍由 Python 与 Ontology 负责；业务语义规则可在 Markdown 维护。
- 行动和权限均明确标为“尚未启用的执行控制”，不会误导为已自动执行。
