# 科技型企业本体设计与维护手册（V0.8）

> 版本：V0.8  
> 用途：统一表达科技型企业知识，用于企业画像、历史案例比较和新案例辅助分析。

---

## 1. 设计目标

本 Ontology 不是企业评分表，也不是跨企业知识图谱。

它的作用是规定：

```text
一家科技型企业应该从哪些方面被描述
每类信息使用什么结构表达
不同来源的陈述如何区分
每项知识如何绑定原始证据
未知、冲突和待核实信息如何保存
```

历史案例和新案例使用同一套 Ontology：

```text
历史材料 → HistoricalEnterpriseProfile
当前材料 → CurrentEnterpriseProfile
```

区别在于用途和审核状态，不在于概念体系。

---

## 2. 基本原则

1. **企业画像优先**  
   目标是完整、真实、可解释地描述一家企业，而不是为了构图而构图。

2. **结构化不等于数值化**  
   信息可以是数值、文本、状态、对象关系、事件或未知项。

3. **陈述不等于事实**  
   企业自述、审计信息、监管认定、司法认定和内部分析必须区分。

4. **重要内容必须绑定证据**  
   每项知识应尽可能保留来源、位置、原文和统计期间。

5. **未知和冲突是正式状态**  
   不得用空字符串或模型猜测代替。

6. **核心 Ontology 保持通用**  
   人工智能、半导体、生物医药等行业特有内容以后通过扩展模块增加。

### 2.1 核心字段准入标准

新增核心字段不能以某一次测试或某一家企业的缺失项为直接依据。候选字段必须同时满足：

1. **跨行业适用**：适用于多数科技型企业，或适用于科技企业中稳定存在的一类共同业务；
2. **审查重要**：能够影响企业身份、技术能力、知识产权、商业化、持续经营或偿债分析；
3. **可稳定取证**：通常可以从企业材料、审计材料、监管材料或其他明确来源中取得；
4. **语义稳定**：不同企业、不同期间使用时含义基本一致；
5. **不可替代**：不能由已有字段、关系或 EvidenceUnit 原文直接等价表达；
6. **可比较和追溯**：能够保留证据，数值字段能够保留统计期间和单位。

以下情况不进入核心 Ontology：

```text
单一企业特有的产品型号、工艺名称或内部指标
仅因一次模型输出无法映射而临时增加的字段
可以作为现有字段明细保存、但没有独立比较价值的细分口径
长期无法稳定取得证据或需要模型主观推断的指标
行业特有且不适用于一般科技企业的内容
```

V0.3 按上述标准补充了主营业务、关键人员、技术来源、核心知识产权、专利总量、产品商业化阶段及主要财务字段。V0.4 进一步补充跨行业稳定披露、能够影响科技企业团队能力和外部依赖分析的非财务信息：关键人员教育背景、职业经历、股权激励计划状态、客户集中度和供应商集中度。

V0.5 将新画像的人员分析粒度由“为多人逐项建立教育和职业经历记录”调整为“保留少量关键人员名称，并形成核心团队教育结构和职业背景概况”。人物级 EvidenceUnit 继续作为汇总事实的可追溯来源；V0.4 的个人教育、职业经历字段和关系仅用于读取既有画像。

“是否具有相关行业经验”不作为事实字段。Ontology 先保存有证据支持的职业经历，再由分析层结合企业主营业务判断相关性，避免在事实层引入主观结论。境内外专利数、发明专利细分、具体产线和产品型号仍不进入核心 Ontology。

## 3. 核心对象

第一版保留以下核心对象即可：

| 对象 | 含义 |
|---|---|
| `Enterprise` | 被分析企业、子公司和关联企业 |
| `Person` | 创始人、实际控制人、高管、核心技术人员 |
| `EducationRecord` | 与明确人员关联的院校、专业、学历或学位记录 |
| `ProfessionalExperience` | 与明确人员关联的任职机构、职位和期间记录 |
| `Organization` | 客户、供应商、银行、投资机构、高校、监管机构等 |
| `Technology` | 核心技术、算法、工艺、平台和技术体系 |
| `IntellectualProperty` | 专利、软著、商标、技术秘密和许可权 |
| `ProductService` | 产品、服务、平台和解决方案 |
| `ResearchProject` | 在研或已完成的研发项目 |
| `FinancingMatter` | 股权融资、债务融资、担保和资金事项 |
| `LegalRiskMatter` | 诉讼、处罚、监管调查和其他重大风险事项 |
| `EvidenceUnit` | PDF 段落、HTML 节点、表格记录等原始证据 |

不需要把每个数字都建成对象。收入、研发费用率、客户集中度等通常作为企业画像字段保存。

## 3.1 两种结构化事实

企业画像的结构化事实分为两种互补形式，不是两套互相替代的本体：

| 类型 | 结构 | 示例 | 当前输出位置 |
|---|---|---|---|
| 属性事实 | 主体 + 字段 + 属性值 | 企业 + `finance.operating_revenue` + 1.2亿元 | `profile_items` |
| 关系事实 | 主体 + 关系 + 客体 | 企业 + `owns` + 某项专利 | `profile_relations` |

两种事实通过主体或对象 ID、证据单元 ID、事实状态和报告期间关联。关联只表示原文支持它们存在联系，不表示系统可以自行推断两条事实必然对应。例如“企业拥有专利”和“授权专利共 73 项”可以共享企业和证据，但不能据此推断 73 项全部对应某一个具体专利。

属性字段适合保存金额、数量、比例、阶段和状态；关系适合保存拥有、开发、销售、采购、合作和依赖等对象之间的联系。Python 分别校验两种结构，不把属性事实强行改写成三元组。

## 4. 企业画像板块

事实层第一版划分为十个板块；这些板块用于组织字段，不等同于最终展示和分析维度。事实到画像维度的映射另见 `prompts/logic/企业画像维度映射.yaml`。

### 4.1 企业基本信息

包括：

```text
法定名称
成立时间
注册资本
企业发展阶段
主营业务
行业和应用领域
主要子公司
```

### 4.2 股权、治理与团队

包括：

```text
实际控制人
主要股东
控制权稳定性
董事和高管
核心技术人员
关键人员教育背景
关键人员职业经历
核心团队教育结构
核心团队职业背景概况
股权激励计划状态
关键人员依赖
团队稳定性
关联方
内部控制情况
```

股权激励计划状态使用以下统一值：

```text
active                 已实施且在当前期间有效
approved_not_started   已批准但尚未实施
planned                仅披露计划或意向
completed              已实施完毕
terminated             已终止
not_applicable         材料明确说明不适用或不存在适用计划
```

未披露股权激励信息不生成状态项，应作为信息缺口处理，不能与 `not_applicable` 混同。

### 4.6 客户、供应商与合作方

包括：


## 5. 核心关系

第一版只保留业务上真正有用的关系：

```text
controls
holds_position_in
has_education
has_professional_experience
owns
claims_to_own
licenses
develops
uses_technology
commercializes_as
depends_on
sells_to
purchases_from
cooperates_with
financed_by
guarantees_for
involved_in
supported_by
contradicted_by
```

示例：

```text
创始人A controls 企业B
核心人员A has_education 教育经历B
实际控制人A has_professional_experience 职业经历C
企业B claims_to_own 技术C
产品D uses_technology 技术C
企业B sells_to 客户E
企业B financed_by 投资机构F
某项陈述 contradicted_by 监管决定G
```

关系必须绑定证据，企业自述形成的关系不能自动视为已确认事实。

## 6. 通用画像字段结构

所有企业画像内容统一使用 `ProfileItem` 表达：

```yaml
ProfileItem:
  item_id: string
  profile_id: string
  section_id: string
  field_id: string

  value_type: string
  value: any
  subject: string | null
  value_scope: string | null
  unit: string | null

  information_status: string
  content_role: string

  reporting_period: string | null
  event_date: string | null

  evidence_refs:
    - evidence_unit_id
      excerpt: string | null

  extraction_method: llm | rule | import | manual
  review_status: string
  ontology_version: string
```

说明：

- `field_id` 使用稳定英文 ID，例如 `technology.maturity_stage`；
- `value` 可以是文本、数字、枚举或对象引用；
- 新画像使用 `team.education_structure` 和 `team.professional_background` 形成企业整体核心团队概况，并引用多条人物级 EvidenceUnit；`team.education_background`、`team.professional_experience` 及其关系仅用于兼容 V0.4 画像；
- 股权激励计划状态使用受控枚举，并保留适用报告期；明确“不适用”应作为有证据支持的状态保存，而不是信息缺失；
- 数量使用 `integer`；总体、地域、类别等统计范围使用 `value_scope` 原样保留，不得把子集改写为总量；
- `subject` 明确属性所属对象，企业整体属性使用 `the_enterprise`；
- 模型抽取必须为每个引用的 EvidenceUnit 提供一条或多条连续原文摘录；摘录不得由模型改写或跨句拼接；
- 字段声明 `value_scope_required: true` 时必须保存统计总体、地域、类别或分母口径；
- `finance.net_profit`、`finance.net_profit_attributable_to_parent`、`finance.adjusted_net_profit_attributable_to_parent` 分别表示普通净利润、归母净利润和扣非归母净利润，不得混用；
- `finance.cash_balance` 只表示期末现金及现金等价物余额；`finance.interest_bearing_debt` 表示债务余额或可核验的债务组成，借款现金流不是债务余额；
- `reporting_period` 用于财务和经营数据；
- `event_date` 只在原文明确或业务确有需要时填写；
- 不强制将历史事实划分为风险前、中、后。

## 7. 信息状态和内容角色

### 7.1 信息状态

```yaml
information_status:
  - claimed
  - supported
  - confirmed
  - disputed
  - contradicted
  - pending_verification
  - insufficient_evidence
  - unknown
  - not_disclosed
  - not_applicable
```

### 7.2 内容角色

```yaml
content_role:
  - enterprise_claim
  - business_record
  - audited_information
  - external_observation
  - regulatory_finding
  - judicial_finding
  - internal_assessment
  - outcome
```

典型规则：

```text
招股说明书中的企业描述
→ enterprise_claim 或 audited_information

监管处罚决定中的认定
→ regulatory_finding

法院裁判中的认定
→ judicial_finding

内部模型形成的判断
→ internal_assessment
```

企业自述不能仅因为被结构化就变成 `confirmed`。

## 8. EvidenceUnit

所有数据源最终转换为可引用的证据单元。

```yaml
EvidenceUnit:
  evidence_unit_id: string
  source_id: string
  case_id: string

  source_type: pdf | html | csv | excel | json | other
  content_type: text_chunk | table_record | structured_record
  content: string | object

  location:
    page: integer | null
    section_path: [string]
    row: integer | null
    columns: [string]
    sheet_name: string | null
    field_path: string | null

  source_date: string | null
  content_hash: string
```

当前实现 PDF 和 HTML，未来增加 CSV、Excel 等时只增加数据源 Adapter，不修改企业画像和 Ontology 的核心接口。

## 9. 必要约束

第一版至少实现以下约束：

```text
审核通过的 ProfileItem 必须绑定 EvidenceUnit
企业自述不得自动标记为 confirmed
监管认定必须来自监管材料
司法认定必须来自司法材料
比率统一存储为 0 至 1
受控枚举字段只能使用 manifest 中列出的值
数量字段必须是非负整数
金额必须包含币种
财务和经营指标必须包含统计期间
关系必须符合允许的对象类型
冲突值不得被静默覆盖
未知信息不得由大模型猜测补全
历史案例结果不得直接转移为新企业事实
```

## 10. ComparisonCard 派生层

完整 `EnterpriseProfile` 是 Ontology 的实例和事实底座。相似案例检索使用从画像派生的 `EnterpriseComparisonCard`，避免要求大模型生成的开放文本值完全相等，也避免将整份长画像直接编码为单个向量。

固定维度为：

```text
enterprise_and_team
technology_and_ip
product_and_commercialization
customer_supplier_and_dependency
finance_and_funding
risk_and_compliance
authority_outcome_and_evidence
```

事实字段的基础分类保存在 Ontology 的 `fact_sections` 中；结构化事实到企业画像调查领域和展示维度的映射保存在 `prompts/logic/企业画像维度映射.yaml`。分析和审批报告中的摘要不是核心 Ontology 字段，也不是事实认定；它们只由已审核画像生成。

```yaml
EnterpriseComparisonCard:
  card_id: string
  profile_id: string
  ontology_version: string
  profile_hash: string
  review_status: pending | approved | rejected

  dimensions:
    - dimension_id: string
      summary: string
      comparison_terms: [string]
      structured_features: {}
      relation_signatures: [string]
      source_item_ids: [string]
      source_relation_ids: [string]
      evidence_unit_ids: [string]
      information_gaps: [string]
```

约束：

- 只从已审核画像生成正式比较卡；
- 摘要和比较词必须引用画像项或画像关系；
- EvidenceUnit 由程序从来源画像项继承；
- 固定标题不进入检索正文；
- 比较卡不能反向修改画像；
- 画像内容、Ontology 版本或画像哈希变化时必须重建；
- 当前企业比较卡只作为查询，不写入历史索引；
- 混合召回分数只用于候选排序，不作为风险结论。

风险模式属于 Ontology 之上的可选业务知识，不属于当前主链路。只有在多个高质量历史画像提供共同证据、存在对照案例并经过人工审核后，才应另行设计和启用；单案例不得直接形成可复用规则。

## 11. 当前文件形式

事实层采用“程序接口本体、业务字段语义、抽取规则、校验规则”四个职责清晰的文件；非专业业务人员只维护字段语义文件，不直接修改程序接口本体。

```text
prompts/data/企业画像本体.yaml
prompts/data/企业画像字段语义.yaml
prompts/data/企业画像抽取规则.yaml
prompts/data/企业画像校验规则.yaml
docs/project/本体设计与维护手册.md
```

YAML 中的 `id`、`section_id`、`value_type` 和 `allowed_values` 是程序接口；`label`、`description`、`synonyms`、`include_when`、`exclude_when` 和 `extraction_notes` 是面向业务人员和模型的字段语义。

文件顶部的 `maintenance_policy` 统一说明维护边界：字段语义可以由业务人员直接调整；字段 ID、类型、枚举、对象类型和关系范围属于稳定程序接口；新增、删除或改名必须同步修改代码、数据库并进行回归测试。

运行时建议：

```text
企业画像本体.yaml
→ 对象、关系、字段和字段级语义

企业画像抽取规则.yaml
→ 通用抽取原则和领域补充规则

企业画像校验规则.yaml
→ 跨字段、跨事实的校验约束

Pydantic
→ 加载和程序校验

JSON
→ 大模型结构化输出和接口传输

SQLite
→ 企业画像、证据和比较卡存储
```

第一版不需要使用 OWL、RDF 或 Neo4j。

## 13. 维护与验证

每个版本至少验证：

```text
能否较完整地描述一家科技型企业
能否区分企业自述、外部支持和权威认定
能否把重要企业知识绑定到原始证据
能否支持不同企业按统一结构比较
能否为相似案例检索和详细比较提供稳定字段
```

不要以字段数量判断 Ontology 质量。字段应满足本规范 2.1 的准入标准；长期缺少材料、无法稳定提取或不能支持分析的字段应删除或合并，具有普适性、重要性且经多个案例验证的缺口才通过新版本增加。

V0.5 为兼容既有画像，运行时仍可读取旧字段 `finance.customer_concentration`、`team.education_background` 和 `team.professional_experience`；新画像必须使用 `customer_supplier.customer_concentration`、`team.education_structure` 和 `team.professional_background`，旧字段不再进入领域抽取白名单。Ontology 版本变化后应重新生成 ComparisonCard，旧画像事实不得被静默覆盖。

V0.6 增加通用 `subject`、`value_scope` 和证据摘录约束，并增加 `intellectual_property.rights_restriction_status`，用于区分知识产权权属与质押、查封、冻结等权利限制。专利地域和类型不扩展为企业专用字段，统一由 `value_scope` 保留。

V0.7 将证据摘录扩展为按 EvidenceUnit 对应的 `evidence_quotes` 数组；引用多条证据时，每条证据必须有自己的连续原文摘录。客户和供应商集中度启用 `value_scope_required`，分别保留前五大客户及收入分母、前五大供应商及采购分母。财务利润口径拆分为普通净利润、归母净利润、扣非归母净利润；现金余额明确为期末现金及现金等价物余额，有息负债只接受债务余额或组成项目，不能使用借款现金流替代。候选实体被拒绝时，其引用关系同步拒绝；重复实体合并时，关系重定向到保留项。

V0.8 在集中度之外增加通用交易对手画像：`customer_supplier.counterparty_name` 保存材料披露的正式名称或匿名代称；`transaction_amount`、`transaction_ratio` 和 `transaction_content` 按主体和报告期保存逐行交易事实；`related_party_status` 保存材料明确披露的主要交易对手关联关系状态。企业到客户复用 `sells_to`，企业到供应商复用 `purchases_from`。匿名代称不得补全真实企业，并形成信息缺口。客户表与供应商表分批抽取，Python按同一表格行校验名称、年度、金额、比例和交易内容，并合并重复关系。
