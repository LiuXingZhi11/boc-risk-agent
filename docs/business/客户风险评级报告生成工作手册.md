# 客户风险评级报告生成工作手册

## 1. 文档定位

本手册用于指导“企业画像 + 行业背景画像 + 同行比较”生成科技金融客户风险评级报告的后续实现。

最终交付物不是企业画像本身，而是业务人员能够直接阅读的：

1. 按《科技金融专属授信业务审批指引》组织的分项审批报告；
2. 各审批方向的一句话总结、审批点判断和样本内排名赋分；
3. 面向授信人员的企业综合核心风险判断。

企业画像、行业背景画像和同行企业指标都是报告的事实材料，不决定最终报告目录。最终报告目录以授信审批指引为准。

## 2. 总体设计原则

### 2.1 指引决定报告结构

企业画像的十个调查领域继续作为材料抽取和事实管理方式，不要求与授信审批条目一一对应。

一个授信审批条目可以使用多个企业画像领域中的少量事实；一个企业画像事实也可以支持多个审批条目。

### 2.2 企业事实是判断主体

每个审批判断必须以当前企业事实、同行指标或明确的信息缺口为基础。行业背景只能说明外部环境和参照标准，不能单独证明企业存在优势或风险。

### 2.3 每个审批点只使用适量信息

为保证系统稳定、提示词清晰和模型输出一致，单个审批点默认输入：

- 3～5条企业画像事实；
- 1～2条行业背景要点；
- 0～2个同行可比指标；
- 必要的信息缺口或冲突。

单个审批点原则上不超过8条核心输入。没有必要的信息不进入模型上下文，不为了追求完整而堆积材料。

### 2.4 不强行得出结论

- 企业事实不足：输出“信息不足，暂不能判断”；
- 行业材料不足：保留企业判断，说明缺少行业基准；
- 同行数据不足：不排名、不赋分；
- 材料存在冲突：保留冲突并说明判断边界；
- 不使用行业事实代替企业事实。

### 2.5 指标排名、方向排名和排名赋分分开处理

单个企业的分方向审批报告是大模型生成的自然语言判断，不能由 Python 直接对文字评分。系统必须区分三件事：

1. **指标排名**：收入、研发费用率、专利数量等统一口径的数值指标，由 Python 计算样本内排名；
2. **方向综合排名**：同一同行样本内全部企业完成该方向报告后，由大模型按照固定比较标准进行横向排序；
3. **排名赋分**：Python 对大模型返回的方向排名进行校验，再转换成名次分。

方向综合排名不直接比较报告文笔，而是比较每家企业结构相同的精简比较卡。比较卡只包含本方向的一句话结论、审批点判断、少量关键事实、可比指标结果和信息缺口。

方向排名赋分使用简单规则：

```text
方向名次分 = 本方向可比较企业数 - 稠密名次 + 1
```

并列企业使用相同名次和相同名次分。信息明显不足、无法形成同口径比较的企业标记为“不可比较”，不自动排在最后，也不赋分。

数值指标排名可以作为方向综合比较的依据，但不能简单取多个指标名次分的平均值代替技术实力、企业规范性等自然语言综合判断。

报告必须写“样本内方向排名”或“样本内排名赋分”，不得表述为全行业排名或银行信用评分。只有一家企业时只能生成审批判断，不能生成真实的样本内方向排名。

### 2.6 简洁优先

本阶段不追求复杂 Agent、自动规划、多轮自我反思或无限检索。企业画像和行业画像完成后，报告阶段使用固定流程组装材料并调用模型生成自然语言判断。

## 3. 输入材料

### 3.1 当前企业画像

只使用已审核接受的企业画像项、关系、信息缺口和冲突。企业画像仍由以下十个调查领域产生：

1. 企业与控制；
2. 团队；
3. 技术与知识产权；
4. 产品与项目；
5. 市场与商业化；
6. 客户与供应商；
7. 财务与融资；
8. 风险事项；
9. 权威认定；
10. 结果与处置。

### 3.2 行业背景画像

只使用已审核接受的行业要点。行业背景维度保持为：

1. 行业发展阶段；
2. 市场规模与增长；
3. 技术路线；
4. 产业链与价值链；
5. 竞争格局；
6. 商业化；
7. 政策与监管；
8. 行业风险。

### 3.3 同行企业比较

同行比较只使用已批准的同行样本、指标定义和指标值。比较前必须统一报告期、币种、单位、统计范围和指标口径。

不能统一口径的数值不参与排名，应记录为信息缺口。

如需检验跨报告期企业进入流程后的表现，只能建立独立的“假设口径试验样本”：同行样本名称和入样规则必须明确列出被假设为目标年度的企业及其原始报告期；企业画像中的原始报告期不得改写；试验报告和方向排名必须向模型传入该假设说明，且不得批准为正式授信结论或与正式同期样本混用。

#### 3.3.1 指标候选的通用口径归一

企业画像保留原始数值、原始单位、统计范围和证据，绝不在画像层改写事实。生成同行指标候选时，Python 仅可执行以下确定性转换：

1. 对金额字段在 `元`、`万元`、`亿元`之间换算到指标定义指定单位；
2. 对原始单位为空的比例字段，以“比例（小数）”作为比较单位；
3. 对主体明确为企业整体、但原始统计范围为空的事实，标记为“企业整体披露，合并范围以原报告为准”；不得据此推断为母公司口径或合并口径；
4. 单位无法换算、主体或统计范围不符合指标定义、或同一企业存在多个无法确定优先级的候选时，不生成该指标值。

实现步骤：先由候选函数返回换算后的比较数值及标准口径，再由人工选择一个有来源画像项和证据引用的候选值。验收时，原始画像项保持不变；指标值能回溯到原始画像项；不同原始金额单位在同一目标单位下可比较；不确定口径仍被排除而非强行排名。

同行样本和指标定义从 `pending` 变为 `approved` 时必须原地更新审核状态，不得采用“删除后插入”的写法；否则关联的指标字段绑定、指标值和后续报告可能被外键级联删除。验收时，批准指标定义后其字段绑定仍可被读取。

## 4. 最终报告骨架

“科技企业特点”不单独形成一个审批方向，而是作为所有方向共同遵循的审查原则：关注科技企业轻资产、发展阶段较早、盈利潜力尚未充分体现等特点，同时重点分析技术优势、商业逻辑和成长性，但不因此忽略真实风险。

最终分项报告按照授信审批指引的11个审查方向组织：

1. 行业市场空间；
2. 行业竞争格局；
3. 企业规范性；
4. 技术实力；
5. 股权结构安排；
6. 企业转型发展情况；
7. 核心团队；
8. 股权融资影响；
9. 财务情况；
10. 量化评估工具应用；
11. 反洗钱和制裁合规管理要求。

每个方向的标准输出为：

```text
审批方向
├── 一句话总结
├── 审批点 1
│   ├── 企业现状
│   ├── 行业背景（适用时）
│   ├── 同行比较（适用时）
│   ├── 审批判断
│   ├── 信息缺口
│   └── 证据引用
├── 审批点 2
├── 审批点 3……
└── 样本内方向排名与赋分（完成多企业横向比较后）
```

### 4.1 报告查看方式

系统对一家企业的正常输出包括一份企业综合评定和最多 11 份分方向报告。分方向报告不是重复报告，而是分别回答授信审批指引中的不同问题。

业务主页面的查看顺序固定为：

1. 选择企业；
2. 选择该企业对应的同行样本，即报告批次；
3. 如该企业在该批次下已有综合评定，显示其评级和综合结论；
4. 从该企业该批次的已有结果中选择一个授信审批方向；
5. 只显示该方向版本号最高的一份报告正文、审核状态和下载入口。

主页面不展示跨企业、跨方向混合的全量报告表格，也不以原始报告 ID 作为业务人员的主要选择依据。相同企业、相同批次、相同方向有多个历史版本时，主页面只显示版本号最高的一份；历史版本放在高级工具中查询。

实现步骤：先按 `case_id` 和 `cohort_id` 过滤已保存报告，再按固定的授信指引顺序构造方向选项，最后读取并渲染选中的单份报告。验收时，选择任一企业和报告批次后，方向列表只包含该企业已有的方向；切换方向只更换当前报告，不同时展开其他方向正文。

### 4.2 单一客户风险评级报告

面向业务人员的最终交付物为每家企业、每个同行样本一份“客户风险评级报告”。企业综合评定、11 份分方向报告和方向排名是该报告的内部依据，不再作为需要逐份阅读的并列交付物。

最终报告固定结构如下：

```text
客户风险评级报告
├── 总体结论
│   ├── 推进建议：审慎推进 / 有条件推进 / 不建议推进
│   ├── 客户风险评级：AAA1 … D1（共 21 级）
│   ├── 强约束不通过：x 条
│   ├── 弱约束不通过：y 条
│   ├── 总体判断、主要风险、缓释因素、待核实事项
└── 授信审批指引逐条结论（固定 11 个方向）
    ├── 约束类型：强约束 / 弱约束
    ├── 状态：通过 / 有条件通过 / 不通过 / 信息不足
    ├── 一句话结论
    ├── 同行位置或指标排名（适用时）
    └── 关键证据（默认收起）
```

### 4.3 强弱约束规则

系统只使用“强约束”和“弱约束”两类，不设置第三类或强约束内部等级。

| 授信审批方向 | 约束类型 |
|---|---|
| 行业市场空间 | 弱约束 |
| 行业竞争格局 | 弱约束 |
| 企业规范性 | 弱约束 |
| 技术实力 | 弱约束 |
| 股权结构安排 | 强约束 |
| 企业转型发展情况 | 弱约束 |
| 核心团队 | 弱约束 |
| 股权融资影响 | 弱约束 |
| 财务情况 | 弱约束 |
| 量化评估工具应用 | 弱约束 |
| 反洗钱和制裁合规管理要求 | 强约束 |

强约束只能在当前输入材料明确披露下列硬性触发事实时判定“不通过”：

1. 股权结构安排：授信主体的实际控制人或控制权无法确认，或者存在尚未解决且直接影响主体权属、控制权或还款责任认定的重大权属争议；
2. 反洗钱和制裁合规：已披露且未解除的制裁限制、洗钱相关重大违法，或者依法不得开展相关业务的合规限制。

材料未披露、材料不足、一般性治理瑕疵、未来控制权变动可能性、经营亏损、现金流为负、融资依赖或普通风险事项，均不得作为强约束“不通过”的理由。它们可形成弱约束不通过或信息不足。

量化评估工具应用虽然在展示上归入弱约束，但它只检验指标口径、样本范围和排名适用性，不对企业自身形成“不通过”结论，也不计入弱约束不通过数量。正式同期样本口径可用时，该方向可为“通过”或“有条件通过”；口径不完整时为“信息不足”。假设口径试验样本因包含跨期材料，固定为“信息不足、仅作流程验证”，不得以此压低单家企业的总体建议或客户风险评级。

### 4.4 总体建议规则

Python 不判断企业事实，只根据模型已输出并校验过的 11 条方向状态执行下列确定性规则：

```text
任一强约束不通过                         → 不建议推进
无强约束不通过，存在强约束信息不足
或至少一项弱约束不通过                    → 有条件推进
其余情况                                  → 审慎推进
```

最终报告必须显示强约束不通过条数和弱约束不通过条数。推进建议是风险闸门，客户风险评级是企业综合质量分层，二者不互相替代。客户风险评级采用 21 级固定边界：

| 等级 | 固定边界 |
|---|---|
| AAA1/2/3 | 无失败且无非量化信息不足；按非量化有条件通过方向数 0-1、2-4、5 条及以上分档。 |
| AA1/2/3 | 无失败但存在非量化信息不足；按不确定方向数分档。 |
| A1/2/3、BBB1/2/3、BB1/2/3 | 分别存在 1、2、3 个弱约束不通过，并按不确定方向数分档。 |
| B1/2 | 存在 4 个弱约束不通过；按不确定方向数不超过 2 条或超过 2 条分档。 |
| CCC1 | 存在 5 个及以上弱约束不通过，但未达到 CC 组合门槛。 |
| CC1 | 至少 3 个弱约束不通过且同时包含企业规范性和财务情况。 |
| C1 / D1 | 恰有 1 条 / 至少 2 条强约束不通过。 |

等级由模型基于方向结论写出自然语言依据，但 Python 必须校验其符合上述固定边界。试验样本的量化评估信息不足不影响等级；其他方向的信息不足会影响同组内数字。推进建议与 21 级评级独立计算，不把评级字母或数字直接当作审批决定。

### 4.4.1 方向状态判定规则

“信息不足”只用于当前材料不足以形成实质正面或负面判断的方向，不能用来回避材料中已明确披露的风险事实。

| 状态 | 判定规则 |
|---|---|
| 通过 | 当前材料支持该方向总体可接受，未出现足以影响该方向判断的明确不利事实。 |
| 有条件通过 | 存在需跟踪或缓释事项，但当前材料同时提供了足以支持暂时接受的基础、整改或缓释信息。 |
| 不通过 | 当前材料已披露直接影响该方向的明确不利事实，且现有材料不能证明该风险已解除、已充分缓释或不再影响判断。 |
| 信息不足 | 当前材料没有足够事实形成实质正面或负面判断。 |

同一方向可以同时存在“不通过”和“信息缺口”：前者反映已经明确的风险事实，后者说明仍需补充核实的范围。不得因为存在信息缺口，就将已有明确风险事实改写为“信息不足”。该规则适用于所有弱约束方向；强约束仍只能按第 4.3 节的硬性触发规则判定不通过。

缺少同行可比指标、缺少市场份额、缺少团队背景或其他单项材料，本身只能形成“信息不足”或“有条件通过”，不能单独作为任何弱约束方向“不通过”的理由。弱约束“不通过”必须由当前材料中已披露、直接影响该方向的明确不利事实支撑。

### 4.5 实现步骤与验收

1. 在授信指引定义中为每个方向增加固定约束类型，并维护强约束的硬性触发说明；
2. 新建最终报告数据结构，保存 11 条方向状态、总体建议、21 级客户风险评级、强弱不通过计数、自然语言判断和证据引用；
3. 用已保存的 11 份方向报告和可用方向排名组装有限输入，由模型输出每个方向的状态和简洁结论；
4. Python 校验方向完整性、强弱类型、强约束不通过理由与证据、状态合法性、引用范围、推进建议和 21 级评级固定边界；
5. Python 根据强弱状态计算不通过条数和推进建议，并保存最终报告；
6. 主页面只展示最终报告，11 个方向按指引顺序折叠；旧的分方向报告、排名和综合评定转为“查看依据”；
7. 验收时，11 个方向恰好各出现一次；财务情况为弱约束；强约束不通过必然得到“不建议推进”和 C1/D1；弱约束不通过不会单独改变推进建议为不建议推进；21 级评级与不通过数量、风险覆盖面和信息完整度相符；所有方向结论均可回溯到已保存报告和证据。

最终报告的 11 份来源方向报告和实际可用的方向排名，均由 Python 从当前企业、当前同行样本的已保存结果确定，不要求模型重复输出这些完整来源列表。模型只需输出自然语言结论、11 个方向状态、强约束硬触发信息和所选证据编号；这样可避免模型在固定元数据中误填不适用方向。

## 5. 审批方向与输入信息的适量对应

下表规定每个方向优先使用的信息。实际运行时只选择最相关的少量材料，不要求把表中所有信息全部输入模型。

| 审批方向 | 建议审批点 | 优先企业信息 | 优先行业信息 | 可选同行指标 |
|---|---|---|---|---|

## 5.1 行业背景画像的证据覆盖要求

行业背景画像需要尽量综合已导入的行业材料，但不要求把所有切片原文一次性发送给模型。受控 ReAct 调查按以下要求选择证据：

1. 八个行业维度都必须各进行一次独立目录搜索；
2. 每个维度优先选择不同章节、不同材料来源的证据，避免同一章节重复占满读取额度；
3. 在读取预算允许时，每个维度至少读取 2 条正文，关键维度可读取更多；
4. 两份及以上行业材料存在时，优先保证每份材料都被搜索和读取，不能只使用检索排名靠前的一份；
5. 目录标题只能用于筛选，最终画像只能引用已读取的正文 EvidenceUnit；
6. 提取模型按八个维度分批生成要点，每个维度保留多个互不重复的高价值结论，并保留信息缺口；
7. 证据不足时输出信息缺口，不得为了提高覆盖率补充材料没有明确表达的内容。

### 本次实现需求

- 行业 ReAct 先完成八个维度的首轮搜索，再允许少量补充检索未覆盖的来源、章节和细分主题；
- 将默认模型调用上限保持为 8 次、搜索上限保持为 10 次，避免通过增加模型回合换取覆盖率；
- 将行业 ReAct 的默认正文读取上限由 24 条提高到 36 条，读取工具调用上限提高到 10 次；
- 将单次目录返回上限由 12 项提高到 16 项，为模型提供更多章节和来源候选；
- 在 ReAct 提示词中要求每个维度在预算允许时读取至少 3 条正文，并优先跨来源、跨章节读取；
- 保持行业画像每个维度最多 4 条独立要点，并要求保留不同来源或章节中的独立事实；
- 保持行业画像提取和审核的默认 thinking 输出上限为 24,000 token，避免扩大证据池后批次因输出上限提前失败；
- 扩充通用行业检索概念词，覆盖定义分类、细分市场、区域市场、供应链、利润池、客户验证、法律合规和安全事故等常见行业报告主题；每次维度搜索自动合并该维度的概念词，避免模型只提交少数关键词；
- 保持每个维度单独搜索、证据引用必须来自原文、Python 校验和语义审核流程不变；
- 不增加针对某一份报告、某一家公司或某个产品名称的特殊规则。

### 实现步骤

1. 修改 `IndustryReactLimits` 和行业画像服务入口的默认参数；
2. 扩充通用行业维度检索词，不写入单一报告、企业或产品名称；
3. 修改行业搜索工具，使每个维度搜索自动合并该维度的通用概念词；
4. 修改行业 ReAct 系统提示词，增加补充检索、来源/章节覆盖计划和读取顺序；
5. 更新默认参数测试，补充提示词覆盖要求测试；
6. 运行行业模块单元测试；
7. 使用当前导入的全部行业材料重新执行真实 ReAct 测试，检查读取切片数、来源覆盖数、维度覆盖数、画像要点数和信息缺口。

### 验收标准

- 默认运行最多读取 36 条正文，最多调用读取工具 10 次；
- 每个维度首轮搜索能够覆盖该维度的通用概念主题，并能在目录不足或来源/章节覆盖不足时进行少量补充检索；
- 真实运行中不再只依赖少量重复章节，两个来源均有已读取证据；
- 八个维度均有证据或明确的信息缺口；
- 画像要点数量不因增加读取量而被固定上限过度压缩，新增要点仍需各自绑定直接原文证据；
- 所有最终要点仍能回溯到已读取 EvidenceUnit，且没有因扩大读取量产生无证据结论。

## 6. 审批点定义

审批条目应配置为稳定的业务字典，不在代码提示词中临时拼接企业名称或单次案例结论。

建议结构：

```text
GuidelineApprovalPointDefinition
├── point_id
├── section_id
├── title
├── enterprise_domain_ids
├── enterprise_field_ids
├── industry_dimension_ids
├── metric_ids
├── max_enterprise_items
├── max_industry_insights
├── max_metrics
├── judgment_instruction
└── review_status
```

说明：

- `section_id` 对应授信审批指引方向；
- `enterprise_domain_ids` 允许一个审批点从多个企业画像领域取事实；
- `enterprise_field_ids` 只限定优先字段，不要求与指引条目同名；
- 三个 `max_` 字段控制输入数量；
- `judgment_instruction` 只描述通用判断任务，不写具体企业、产品或测试案例；
- 只有已批准的定义才能进入正式报告。

方向综合排名使用独立的方向定义：

```text
GuidelineSectionDefinition
├── section_id
├── title
├── point_ids
├── comparison_criteria
├── ranking_enabled
├── max_comparison_card_chars
└── review_status
```

- `comparison_criteria` 固定本方向的比较标准，例如技术实力使用技术先进性、稳定性和商业转化可行性；
- `ranking_enabled` 决定该方向是否需要横向排名；
- “量化评估工具应用”等流程性方向可以不单独排名；
- 比较标准只能写通用业务原则，不写企业名称和单次测试结论。

每家企业在一个方向生成一张精简比较卡：

```text
DirectionComparisonCard
├── cohort_id
├── section_id
├── case_id
├── one_sentence_summary
├── approval_point_judgments
├── key_enterprise_item_ids
├── metric_ranking_results
├── information_gaps
└── source_section_report_id
```

方向排名结果保存：

```text
DirectionRankingResult
├── cohort_id
├── section_id
├── comparable_company_count
├── ranking_groups
│   ├── rank
│   ├── case_ids
│   └── comparison_reason
├── not_comparable_case_ids
├── rank_points_by_case
└── review_status
```

## 7. 报告生成流程

```text
已批准企业画像 ───────┐
已批准行业背景画像 ───┼→ 为每家企业按指引条目组装有限上下文
已批准同行指标与排名 ─┘
                              ↓
                    生成单企业分方向审批报告
                              ↓
                    Python 校验并人工批准报告
                              ↓
                    同方向多企业生成精简比较卡
                              ↓
                    大模型按固定标准横向排序
                              ↓
                    Python 校验排名并转换名次分
                              ↓
                    人工批准方向排名结果
                              ↓
                    生成综合核心风险判断
                              ↓
                    人工审核并导出最终报告
```

### 步骤1：加载审批指引字典

按固定顺序加载11个审批方向和其审批点定义。定义缺失时停止生成对应方向，不允许模型自行创造审批点。

### 步骤2：组装审批点上下文

对每个审批点：

1. 从已接受企业画像中选择最相关的3～5条事实；
2. 从已接受行业画像中选择最相关的1～2条行业要点；
3. 加入0～2个已计算的同行指标；
4. 加入与本审批点直接相关的信息缺口和冲突；
5. 保留所有来源 ID 和 EvidenceReference。

材料选择优先使用确定性字段映射和简单排序。只有存在多个相近候选、规则无法稳定选择时，才允许模型做一次受限选择。

### 本轮上限验证：扩大企业事实输入

当前实现将单个审批点的企业事实组上限设为10组，行业要点仍最多2条，同行指标仍最多2条。一个事实组由相同主体（或企业主体）、报告期和统计口径下的相关字段组成；同一组内的名称、金额、比例、成熟度等字段一并传入。该调整只扩大统一的输入预算，不增加企业专用字段、企业名称规则或单次材料补丁。

实施步骤：

1. 将授信审批点默认 `max_enterprise_groups` 设为10；
2. 按主体、报告期和统计口径把相关画像项归并为事实组；
3. 先为每个有候选的允许字段选择至少一个事实组，再用剩余额度选择其他事实组；
4. 保持审批点字段映射、行业要点上限、指标上限和证据校验不变；
5. 重新生成宇树受影响方向报告，比较技术、团队、财务和反洗钱方向是否能使用原画像中已抽取的更多事实。

验收重点：

- 输入事实组不超过10组，组内画像项仍能回溯到画像项和 EvidenceUnit；
- 技术成熟度、团队专业背景、财务现金/利润等已抽取字段能够在适用审批点中出现；
- 客户交易信息仍不足时，要区分“材料未披露”和“上下文未选入”；
- 不因扩大上限而放松模型输出结构和证据引用校验。

### 步骤3：逐方向生成报告

每个审批方向单独调用一次模型。一次调用包含该方向的全部审批点，但每个审批点只能看到自己的允许材料。

报告阶段不使用 ReAct 工具循环，不重新搜索原始 PDF，也不允许模型读取未审核材料。

### 步骤4：校验报告

Python 只执行必要校验：

1. 审批点数量和 ID 与定义完全一致；
2. 引用的企业事实、行业要点、指标和信息缺口都来自输入；
3. 每个有明确判断的审批点至少引用一条企业事实或一个企业指标；
4. 行业材料不能单独支撑企业结论；
5. 报告引用的数值指标和指标名次必须与 Python 结果一致；
6. 一句话总结不得超出本方向审批点结论。

模型重复返回同一个已允许的事实 ID、行业要点 ID、指标 ID 或信息缺口编号时，Python 按首次出现顺序去重后继续校验；未知 ID、越界编号和缺失的必需审批点仍必须拒绝。重复引用不产生新事实，不能作为整份报告失败的理由。

若首次输出仅因 JSON 结构、引用 ID 或编号校验失败，系统可将原输出、校验错误和同一份允许输入回传模型进行一次格式修复；修复调用不得追加原始 PDF、未审核事实或新的业务判断。修复后仍不通过时，报告保持未生成并记录错误，不由 Python 猜测引用对象。

方向排名中，若模型已按正确顺序输出分组、首组标为第 1 名、后续分组名次严格递增，但采用“1、3、4”这类非稠密编号，Python 按分组顺序标准化为“1、2、3”。该转换不改变排序、并列关系或比较理由；首组不是第 1 名、分组乱序、企业重复、企业遗漏或样本外企业仍必须拒绝。

不增加与任务无关的安全性冗余检查，不用大量规则修改模型自然语言。

### 步骤5：人工审核分方向报告

人工审核重点为：

- 企业事实是否使用正确；
- 行业背景是否与企业所属细分领域相关；
- 同行样本和指标口径是否可比；
- 审批判断是否超出证据；
- 信息不足是否被如实保留。

单个企业报告批准后才可进入同方向横向比较。只有一家企业时，流程在本步骤结束，不执行方向排名。

### 步骤6：生成方向比较卡

在同一已批准同行样本内，收集全部企业同一方向的已批准报告，为每家企业生成结构和长度一致的精简比较卡。

比较卡优先使用审批点判断及其引用的关键事实，不直接输入完整企业画像、完整行业画像或长篇原始报告。数值指标的 Python 排名作为辅助依据保留在比较卡中。

### 步骤7：生成方向综合排名

每个启用排名的审批方向调用一次模型，将本方向全部企业比较卡同时输入。模型只能按照该方向已批准的固定比较标准输出：

1. 可比较企业的排序或并列分组；
2. 每个排序分组的简短比较理由；
3. 因信息不足而不可比较的企业 ID。

模型不输出分数，不重新计算数值指标，不增加企业事实。

方向可比性按证据和评价口径判断，不以“没有数值指标”作为唯一不可比理由：

- 两家企业拥有相同审批点结构，且至少有相关企业事实、行业基准或已批准判断时，可以进行定性比较；
- 只有材料严重缺失、统计范围冲突或无法建立同口径判断时，才放入 `not_comparable_case_ids`；
- 如果只能判断相对差异而不能区分名次，可以将企业放入同一并列分组，并在理由中说明信息边界；
- 输入样本有两家及以上且存在共同可比较材料时，不得把全部企业仅因缺少量化指标而列为不可比。

### 步骤8：校验排名并转换名次分

Python 执行必要校验：

1. 同行样本内每家企业必须且只能出现一次，位于排名分组或不可比较列表；
2. 不得出现样本外企业或重复企业；
3. 名次和并列关系必须合法；
4. 按可比较企业数和稠密名次计算方向名次分；
5. 不可比较企业不赋分。

方向排名结果需人工批准后才能进入最终报告。

### 步骤9：生成综合核心风险判断

综合报告只读取已批准的分方向报告和方向排名结果，不重新读取企业画像、行业报告或原始 PDF。

输出内容包括：

1. 企业整体核心风险判断；
2. 主要风险；
3. 优势或风险缓释因素；
4. 判断边界；
5. 优先核实事项；
6. 所引用的分方向报告和原始证据链。

## 8. 大模型与 Python 的职责

### 8.1 大模型负责

- 根据有限且已审核的材料形成自然语言判断；
- 解释企业现状与行业环境、同行位置之间的关系；
- 生成审批点判断和一句话总结；
- 根据同一方向的多企业精简比较卡和固定标准形成相对排序；
- 汇总已批准方向报告，形成综合核心风险判断。

### 8.2 Python 负责

- 加载审批条目和字段映射；
- 控制每个审批点的输入数量；
- 组装企业、行业和同行材料；
- 计算数值指标排名；
- 校验大模型返回的方向综合排名并转换方向名次分；
- 校验模型引用的 ID、审批点数量和名次；
- 保存审核状态、证据引用和最终报告。

Python 不负责通过关键词规则直接形成审批结论，也不大规模改写模型输出。

## 10. 后续实施步骤

### 阶段一：审批条目配置

1. 把授信审批指引的11个方向和子条目写成稳定配置；
2. 为每个审批点配置少量企业领域、企业字段和行业维度；
3. 配置输入数量上限；
4. 配置可选同行指标；
5. 用静态测试确认所有 ID 有效。

### 阶段二：上下文组装

1. 允许一个审批点读取多个企业画像领域；
2. 只读取已接受的企业和行业事实；
3. 按数量上限筛选核心材料；
4. 记录未找到材料的审批点；
5. 保留原始证据引用。

### 阶段三：分方向报告

1. 固定模型输入和 JSON 输出结构；
2. 每个方向调用一次模型；
3. 校验审批点、引用和信息缺口；
4. 导出可读 Markdown；
5. 增加人工批准入口。

### 阶段四：方向综合排名与赋分

1. 复用现有数值指标排名，作为方向比较的辅助材料；
2. 汇总同一同行样本内各企业同一方向的已批准报告；
3. 为每家企业生成结构一致的精简比较卡；
4. 按固定方向标准调用模型形成相对排序和比较理由；
5. Python 校验排序完整性、并列和不可比较企业；
6. Python 将方向名次转换成排名赋分；
7. 增加方向排名结果的人工批准入口。

### 阶段五：综合报告

1. 只输入已批准分方向报告和已批准方向排名结果；
2. 生成核心风险、缓释因素、判断边界和核实事项；
3. 校验引用的方向报告 ID；
4. 保留完整证据链；
5. 导出客户风险评级报告。

### 阶段六：真实材料验证

1. 先选择一家企业和一份对应行业报告验证11个方向的单企业报告；
2. 再选择至少三家可比企业验证同方向横向排名；
3. 检查11个方向是否均能生成或正确报告信息不足；
4. 检查每个审批点是否只使用少量相关信息；
5. 检查是否存在行业材料替代企业事实的错误；
6. 检查模型方向排序是否仅使用比较卡和固定标准；
7. 检查 Python 方向赋分是否与模型返回名次一致；
8. 只修复普遍性问题，不为单一企业或单一产品增加专用规则。

## 11. 验收标准

### 11.1 结构

- 最终报告严格按照授信审批指引的11个方向排序；
- 每个方向包含一句话总结和固定审批点；
- 企业画像十领域不直接作为最终报告目录；
- 综合报告能够汇总已批准的分方向结论。

### 11.2 内容

- 每个明确判断至少有当前企业事实或企业指标支持；
- 行业背景只承担环境基准作用；
- 单个审批点默认不超过8条核心输入；
- 信息不足时能够稳定输出判断边界；
- 不编造企业事实、行业事实、名次或评分。

### 11.3 排名

- 数值指标排名只来自口径一致的已批准指标，并由 Python 计算；
- 方向综合排名只比较同一同行样本内已批准的同方向报告；
- 方向排名使用固定比较标准和结构一致的精简比较卡；
- 每家样本企业只能出现一次，位于排名结果或不可比较列表；
- 并列、缺失、不可比较和正负向指标处理正确；
- 报告明确写出样本范围；
- 方向赋分可以回溯到大模型方向排名和对应比较卡；
- 大模型不直接输出方向分，Python 不直接评价自然语言结论。

### 11.4 可追溯性

- 审批点可以回溯到企业画像项、行业要点和同行指标；
- 企业画像项和行业要点可以继续回溯到 EvidenceUnit；
- 方向排名可以回溯到各企业精简比较卡和已批准分方向报告；
- 综合核心风险判断可以回溯到已批准的分方向报告。

## 12. 当前阶段不做的内容

- 不让模型自由决定最终报告目录；
- 不要求企业画像字段与授信指引逐字对应；
- 不为每个审批条目输入全部相关事实；
- 不强制所有方向排名或赋分；
- 不让模型自行计算数值指标、指标名次或方向分；
- 不让 Python 直接对自然语言审批判断评分；
- 不在报告阶段重新运行复杂 ReAct 检索；
- 不为单次测试企业增加专用提示词或关键词补丁；
- 不追求一次性覆盖所有银行内部量化模型和业务规则。

## 13. 难度与工作量评估

### 13.1 总体判断

该任务整体为中等偏高难度，但不需要推翻现有系统。当前项目已有企业画像、行业画像、同行数值指标排名、分方向报告模型、SQLite 仓库和人工审核基础，可以复用。

主要难点不是 ReAct 或 PDF 抽取，而是：

1. 把最终报告主键从企业画像领域调整为授信审批指引方向；
2. 允许一个审批点从多个企业画像领域取少量事实；
3. 保证多家企业方向比较使用相同结构和固定标准；
4. 控制大模型方向排序的稳定性，并正确处理并列和不可比较；
5. 准备并批准足够多、口径一致的企业画像用于真实排名。

### 13.2 分项工作量

以下估算以一名熟悉当前代码的开发人员为基准，不包含收集新企业 PDF 的时间。

| 工作项 | 难度 | 预计工作量 |
|---|---:|---:|
| 授信指引方向、审批点和比较标准配置 | 中 | 1～2人日 |
| 调整审批模型和数据库结构 | 中 | 1～2人日 |
| 多企业画像领域的有限上下文组装 | 中 | 2～3人日 |
| 11方向单企业报告生成与校验 | 中 | 2～3人日 |
| 精简方向比较卡 | 中 | 1～2人日 |
| 大模型方向综合排名、并列和不可比较处理 | 中高 | 2～4人日 |
| Python 排名校验和名次分转换 | 低到中 | 1人日 |

### 13.3 十家企业时的额外工作量

十家企业的主要新增成本来自材料处理、画像人工审核和模型调用，不是排名代码本身。

按照每家企业11个方向分别生成报告的设计，十家企业约需要：

- 110次单企业方向报告调用；
- 约9～10次方向横向排名调用；
- 10次企业综合报告调用；
- 合计约129～130次报告阶段模型调用，不包含企业画像和行业画像抽取。

如果十家企业已有完整、已批准的企业画像，完成十企业真实验证预计额外需要5～8人日。如果还需要从年报重新生成、审核并补齐十家企业画像，整体还需额外增加约2～3周。

### 13.4 推荐实施范围

第一轮先完成三家企业的可用闭环：

1. 实现全部11个审批方向的单企业报告；
2. 选择3～5个最有代表性的方向验证横向排名；
3. 确认比较卡、固定标准、不可比较处理和排名赋分稳定；
4. 再扩展到其余可排名方向和十家企业。

该范围能够验证核心设计，又不会在第一轮投入大量模型调用和人工审核工作。
